---
title: Fluxo de Enrollment Biométrico
description: Passo a passo do cadastro de uma digital biométrica — desde a solicitação no portal até a sincronização do template nos controladores físicos.
---

O enrollment biométrico é o processo de cadastrar a digital de um usuário no sistema. Em vez de um dispositivo dedicado, qualquer fechadura online com sensor ZN-53X pode ser temporariamente convertida em **modo terminal** para capturar o template biométrico.

---

## Visão geral

```
Admin inicia enrollment no portal
        │
        ▼
POST /users/:id/fingerprints/enroll-request
  { finger: "RIGHT_INDEX", controllerId: "ctrl-bloco-a-lab-101" }
        │
        ▼
Backend cria enrollment_request (TTL: 2 min)
Backend publica: door/{controllerId}/enter-enrollment-mode
        │
        ▼
Fechadura entra em MODO TERMINAL
  → LED azul pulsante
  → Ignora tentativas de acesso normais
  → Aguarda 2 passagens do dedo
        │
        ▼
Usuário apresenta o dedo 2x ao sensor ZN-53X
        │
        ▼
Fechadura publica: door/{id}/enrollment-result
  { enrollmentId, template: "hex...", quality: 85, status: "SUCCESS" }
        │
        ▼
Broker chama: POST /iot/enrollment/complete
Backend persiste access_credential
Backend sincroniza template em todos os controladores compatíveis
        │
        ▼
Cada controlador confirma: door/{id}/sync-result
Backend atualiza controller_credential_slot
        │
        ▼
Portal confirma o cadastro (polling GET /iot/enrollment/:id/status)
```

---

## Etapas detalhadas

### Etapa 1 — Solicitação pelo administrador

O administrador acessa o drawer de gerenciamento de digitais de um usuário no portal (`FingerprintHandDrawer`), seleciona o dedo no diagrama SVG interativo e escolhe uma fechadura online para realizar a captura.

Ao confirmar, o frontend chama:

```http
POST /users/:id/fingerprints/enroll-request
Content-Type: application/json

{
  "finger": "RIGHT_INDEX",
  "controllerId": "ctrl-bloco-a-lab-101"
}
```

**Validações realizadas pelo backend:**
- O usuário existe
- O dedo informado é válido (um dos 10 valores do enum `FingerEnum`)
- Não existe outra digital cadastrada para este dedo deste usuário
- O controlador está registrado no sistema
- O controlador possui `sensorProtocol` compatível (R30X para ZN-53X)

---

### Etapa 2 — Criação do enrollment_request

O backend cria um registro em `enrollment_request` com os seguintes dados:

```json
{
  "id": "01951234-abcd-7000-8000-000000000060",
  "userId": "7b3cf58e-353f-48de-b2fd-6f203d64d3f8",
  "controllerId": "ctrl-bloco-a-lab-101",
  "finger": "RIGHT_INDEX",
  "status": "PENDING",
  "expiresAt": "2025-07-01T12:02:00.000Z",
  "createdAt": "2025-07-01T12:00:00.000Z"
}
```

O TTL padrão é de **2 minutos** a partir da criação. Após esse período, o enrollment expira automaticamente e a fechadura retorna ao modo normal.

---

### Etapa 3 — Ativação do modo terminal na fechadura

Imediatamente após criar o `enrollment_request`, o backend publica via broker MQTT:

```
Tópico: door/ctrl-bloco-a-lab-101/enter-enrollment-mode

Payload:
{
  "enrollmentId": "01951234-abcd-7000-8000-000000000060",
  "userId": "7b3cf58e-353f-48de-b2fd-6f203d64d3f8",
  "finger": "RIGHT_INDEX",
  "expiresAt": "2025-07-01T12:02:00.000Z"
}
```

A resposta ao frontend inclui o `enrollmentId` e o `expiresAt` para que o portal possa iniciar o polling de status e exibir um countdown.

---

### Etapa 4 — Captura biométrica (Firmware)

Ao receber `enter-enrollment-mode`, o firmware:

1. **Para de processar acessos normais** — o relé permanece inativo
2. **Acende o LED azul** em modo pulsante para indicar que está aguardando
3. **Inicia a rotina de enrollment** do protocolo R30x:

```
Passagem 1: GenImg() → Img2Tz(buffer 1)
Passagem 2: GenImg() → Img2Tz(buffer 2)
CreateModel() — combina os dois buffers
GetModel()    — extrai o template final (256 bytes)
UploadTemplate(0x08) — transfere via SoftwareSerial
```

4. **Extrai o template** como string hexadecimal de 512 caracteres (256 bytes × 2 chars/byte)
5. **Publica o resultado** e retorna ao modo fechadura imediatamente

Se o usuário não apresentar o dedo antes de `expiresAt`, o firmware publica automaticamente com `status: "EXPIRED"` e retorna ao modo fechadura.

---

### Etapa 5 — Publicação do resultado (Firmware → Broker)

```
Tópico: door/ctrl-bloco-a-lab-101/enrollment-result

Payload (sucesso):
{
  "enrollmentId": "01951234-abcd-7000-8000-000000000060",
  "template": "a3f9c2e1d4b8e72f9c3a...",  // 512 chars hex
  "quality": 85,
  "status": "SUCCESS"
}

Payload (falha):
{
  "enrollmentId": "01951234-abcd-7000-8000-000000000060",
  "template": null,
  "quality": 0,
  "status": "FAILED"
}

Payload (expiração):
{
  "enrollmentId": "01951234-abcd-7000-8000-000000000060",
  "template": null,
  "quality": 0,
  "status": "EXPIRED"
}
```

**A fechadura retorna ao modo fechadura imediatamente** após publicar esta mensagem, independentemente do status.

---

### Etapa 6 — Persistência da credencial (Backend)

O broker recebe `enrollment-result` e chama `POST /iot/enrollment/complete`. O backend:

1. **Valida o `enrollmentId`** — deve existir e ter `status: "PENDING"`
2. **Verifica se ainda não expirou** — compara `expiresAt` com o timestamp atual
3. **Insere `access_credential`** no banco:

```json
{
  "id": "01951234-abcd-7000-8000-000000000050",
  "userId": "7b3cf58e-353f-48de-b2fd-6f203d64d3f8",
  "type": "FINGERPRINT",
  "value": "a3f9c2e1d4b8e72f9c3a...",
  "finger": "RIGHT_INDEX",
  "enrolledByControllerId": "ctrl-bloco-a-lab-101",
  "createdAt": "2025-07-01T12:00:45.000Z"
}
```

O campo `enrolledByControllerId` rastreia qual fechadura foi usada para a captura — útil para auditoria e diagnóstico.

4. **Atualiza `enrollment_request.status`** para `"SUCCESS"`

---

### Etapa 7 — Sincronização nos controladores

Após persistir a credencial, o backend identifica todos os controladores que devem receber o novo template:

```
Critério de sincronização:
  door_controller.sensorProtocol = access_credential.sensorProtocol
  (apenas controladores com o mesmo tipo de sensor recebem o template)
```

Para cada controlador elegível, o broker publica:

```
Tópico: door/{controllerId}/sync-credentials

Payload:
{
  "credentials": [
    {
      "slotId": 3,
      "credentialId": "01951234-abcd-7000-8000-000000000050",
      "template": "a3f9c2e1d4b8e72f9c3a..."
    }
  ]
}
```

> ℹ️ A sincronização inclui a própria fechadura que realizou o enrollment — ela também precisa carregar o template no slot correto do ZN-53X para futuros acessos.

---

### Etapa 8 — Confirmação pelos controladores

Cada controlador:

1. Chama `storeModel(slotId, template)` no ZN-53X para carregar o template no slot indicado
2. Publica `door/{id}/sync-result` confirmando os slots carregados:

```json
{
  "loadedSlots": [
    { "slotId": 3, "credentialId": "01951234-abcd-7000-8000-000000000050" }
  ],
  "evictedSlots": []
}
```

O broker repassa ao backend via `POST /iot/devices/:id/sync-result`, que atualiza `controller_credential_slot`:

```json
{
  "controllerId": "ctrl-bloco-a-lab-101",
  "slotId": 3,
  "credentialId": "01951234-abcd-7000-8000-000000000050",
  "syncedAt": "2025-07-01T12:01:00.000Z",
  "lastUsedAt": null
}
```

---

### Etapa 9 — Confirmação no portal

O frontend faz polling em `GET /iot/enrollment/:enrollmentId/status` a cada 2 segundos enquanto o drawer de enrollment está aberto:

```json
{
  "enrollmentId": "01951234-abcd-7000-8000-000000000060",
  "status": "SUCCESS",
  "finger": "RIGHT_INDEX",
  "userId": "7b3cf58e-353f-48de-b2fd-6f203d64d3f8",
  "controllerId": "ctrl-bloco-a-lab-101",
  "expiresAt": "2025-07-01T12:02:00.000Z",
  "createdAt": "2025-07-01T12:00:00.000Z"
}
```

Ao detectar `status: "SUCCESS"`, o frontend:
- Para o polling
- Invalida a query de fingerprints do usuário (`["users", userId, "fingerprints"]`)
- Exibe confirmação visual no drawer
- Atualiza o badge de contagem de digitais na tabela de usuários

---

## Cancelamento manual

O administrador pode cancelar um enrollment em andamento pelo portal. O frontend chama um endpoint que:

1. Atualiza `enrollment_request.status = "CANCELLED"` no banco
2. Publica via broker:

```
Tópico: door/ctrl-bloco-a-lab-101/cancel-enrollment

Payload:
{
  "enrollmentId": "01951234-abcd-7000-8000-000000000060"
}
```

A fechadura retorna ao modo fechadura imediatamente ao receber este tópico e publica `enrollment-result` com `status: "FAILED"`.

---

## Casos de erro

| Situação | Comportamento |
|---|---|
| Dedo já cadastrado para este usuário | `POST /enroll-request` retorna `409 Conflict` |
| Controlador offline | `POST /enroll-request` retorna `404 Not Found` |
| Usuário não apresenta o dedo a tempo | Firmware publica `status: "EXPIRED"` ao atingir `expiresAt` |
| Qualidade da digital insuficiente | Firmware publica `status: "FAILED"`, admin deve reiniciar |
| Template duplicado (mesmo usuário, outro dedo, mesmo padrão biométrico) | Banco rejeita via constraint `UNIQUE` — `409 Conflict` |
| Broker cai durante o enrollment | Firmware expira por TTL e retorna ao modo fechadura |

## Gestão de slots no ZN-53X

O sensor ZN-53X suporta até **127 slots** de templates biométricos (slots 1–127). O sistema mantém um mapa de qual credencial ocupa qual slot em cada controlador via `controller_credential_slot`.

### Política de eviction (HW-008 — pendente)

Quando todos os slots estão ocupados e um novo template precisa ser carregado, o sistema aplica eviction baseado em `lastUsedAt`:

```
1. Identificar o slot com lastUsedAt mais antigo
2. Remover o template do ZN-53X (deleteModel)
3. Atualizar controller_credential_slot (remover mapeamento antigo)
4. Carregar o novo template no slot liberado
5. Confirmar com sync-result
```

> ⚠️ **Status:** a política de eviction (HW-008) ainda não está implementada. Atualmente, o sistema assume que há slots disponíveis.

---

## Referência de estados do enrollment_request

| Status | Descrição | Próximo estado possível |
|---|---|---|
| `PENDING` | Aguardando captura na fechadura | `SUCCESS`, `FAILED`, `EXPIRED`, `CANCELLED` |
| `SUCCESS` | Digital capturada e credencial persistida | — (terminal) |
| `FAILED` | Captura falhou (qualidade insuficiente) | — (terminal) |
| `EXPIRED` | TTL expirou sem captura | — (terminal) |
| `CANCELLED` | Cancelado manualmente pelo admin | — (terminal) |

Estados terminais não podem ser revertidos — um novo `enrollment_request` deve ser criado para tentar novamente.
