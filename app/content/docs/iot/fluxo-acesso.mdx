---
title: Fluxo de Acesso
description: Detalhamento completo do fluxo de verificação de acesso — desde a apresentação da credencial até o acionamento da fechadura.
---

O fluxo de acesso é acionado toda vez que um usuário apresenta uma credencial (digital biométrica ou tag NFC) ao controlador instalado em uma porta. O processo envolve quatro componentes: o **firmware** (ESP8266), o **broker MQTT** (Aedes), o **backend** (Fastify) e o **banco de dados** (PostgreSQL).

---

## Diagrama completo

```
Usuário apresenta credencial (digital ou NFC)
        │
        ▼
[FIRMWARE — ESP8266]
  Lê credencial via ZN-53X ou IC V1.3A
        │
        ▼
  Publica: door/{id}/access-attempt
  {
    credentialType: "FINGERPRINT",
    credentialValue: "a3f9c2e1...",
    timestamp: "2025-07-01T12:00:00.000Z"
  }
        │
        ▼
[BROKER MQTT — Aedes]
  Recebe e valida o payload
        │
        ▼
  POST /iot/access → [BACKEND — Fastify]
  {
    controllerId: "ctrl-bloco-a-lab-101",
    credentialValue: "a3f9c2e1...",
    credentialType: "FINGERPRINT"
  }
        │
        ▼
[BACKEND — Fastify]
  processAccessAttempt(controllerId, credentialValue, credentialType)
        │
        ├── 1. Busca door_controller por controllerId
        │         → obtém roomId
        │
        ├── 2. Busca access_credential por credentialValue + credentialType
        │         → obtém userId
        │
        ├── 3. Executa verifyAccess(userId, roomId)
        │         ├── PERM-001: user_room_permission
        │         ├── PERM-002: user_room_type_permission
        │         ├── PERM-003: profile_room_permission (via user_profile)
        │         └── PERM-004: profile_room_type_permission (via user_profile)
        │
        └── 4. Insere access_log
                  { decision: "GRANTED" | "DENIED", reason, userId, roomId }
        │
        ▼
  Resposta retorna ao broker
  { decision: "GRANTED", userId: "...", userName: "Ana Souza" }
        │
        ▼
[BROKER MQTT — Aedes]
  Publica: door/{id}/access-result
  { decision: "GRANTED", userId: "...", userName: "Ana Souza" }
        │
        ├── Se GRANTED:
        │     Enfileira comando UNLOCK → POST /iot/devices/:id/commands
        │     Publica: door/{id}/command { command: "UNLOCK", expiresAt: ... }
        │
        └── Se DENIED:
              Nenhuma ação adicional
        │
        ▼
[FIRMWARE — ESP8266]
  Recebe door/{id}/access-result
        │
        ├── GRANTED → aciona relé (UNLOCK por 3–5s), LED verde, buzzer curto
        └── DENIED  → mantém relé, LED vermelho, buzzer longo
```

## Etapas detalhadas

### Etapa 1 — Leitura da credencial (Firmware)

O firmware opera em um loop não-bloqueante usando `millis()`. A leitura de credenciais acontece de forma orientada a eventos:

**Biometria (ZN-53X via SoftwareSerial):**
1. O sensor detecta um dedo via IRQ ou polling
2. O firmware chama a rotina de identificação do protocolo R30x
3. Se a correspondência for encontrada localmente (matching on-device), o template é extraído
4. O template em hexadecimal (512 chars) é incluído no payload

**NFC (IC V1.3A — Wiegand 26):**
1. O leitor detecta uma aproximação de tag
2. Os bits D0/D1 do protocolo Wiegand são decodificados via interrupção
3. O UID da tag (ex: `04:AB:CD:EF:12`) é incluído no payload

O timeout para aguardar `door/{id}/access-result` após publicar a tentativa é de **3 segundos**. Se não houver resposta, o firmware aplica a política offline (HW-008 — pendente de implementação).

---

### Etapa 2 — Recepção e roteamento (Broker)

O broker Aedes recebe a mensagem no handler de `publish` e extrai o `controllerId` do tópico:

```
topic: "door/ctrl-bloco-a-lab-101/access-attempt"
                │
                └── controllerId = "ctrl-bloco-a-lab-101"
```

O payload é validado via **Zod** antes de ser encaminhado ao backend. Payloads inválidos são descartados com log de erro — nunca relançados.

---

### Etapa 3 — Verificação de acesso (Backend)

A função `processAccessAttempt` executa a lógica central:

#### 3a. Resolução do controlador

```sql
SELECT room_id FROM door_controller
WHERE id = $controllerId
LIMIT 1;
```

Se o controlador não for encontrado, registra log com `reason: "CONTROLLER_NOT_FOUND"` e retorna `DENIED`.

#### 3b. Identificação do usuário

```sql
SELECT user_id FROM access_credential
WHERE value = $credentialValue
  AND type  = $credentialType
LIMIT 1;
```

Se nenhuma credencial corresponder, registra log com `reason: "CREDENTIAL_NOT_FOUND"` e retorna `DENIED`.

#### 3c. Verificação de permissão

A função `verifyAccess(userId, roomId)` consulta os 4 níveis em paralelo:

```sql
-- PERM-001: permissão direta usuário → sala
SELECT 1 FROM user_room_permission
WHERE user_id = $userId AND room_id = $roomId;

-- PERM-002: permissão usuário → tipo de sala
SELECT 1 FROM user_room_type_permission urtp
JOIN room r ON r.type_id = urtp.room_type_id
WHERE urtp.user_id = $userId AND r.id = $roomId;

-- PERM-003: permissão perfil → sala (via user_profile)
SELECT 1 FROM profile_room_permission prp
JOIN user_profile up ON up.profile_id = prp.profile_id
WHERE up.user_id = $userId AND prp.room_id = $roomId;

-- PERM-004: permissão perfil → tipo de sala (via user_profile)
SELECT 1 FROM profile_room_type_permission prtp
JOIN user_profile up ON up.profile_id = prtp.profile_id
JOIN room r ON r.type_id = prtp.room_type_id
WHERE up.user_id = $userId AND r.id = $roomId;
```

Retorna `true` se **qualquer** consulta retornar resultado.

Se nenhuma permissão for encontrada, registra log com `reason: "PERMISSION_DENIED"` e retorna `DENIED`.

#### 3d. Registro de log

Independentemente da decisão, um registro é inserido em `access_log`:

```json
{
  "id": "01951234-abcd-7000-8000-000000000070",
  "controllerId": "ctrl-bloco-a-lab-101",
  "roomId": "cdea3efb-650d-4c8a-a9c0-8ee97d739f5c",
  "userId": "7b3cf58e-353f-48de-b2fd-6f203d64d3f8",
  "credentialType": "FINGERPRINT",
  "decision": "GRANTED",
  "reason": null,
  "accessedAt": "2025-07-01T12:00:00.000Z"
}
```

---

### Etapa 4 — Publicação do resultado (Broker)

O broker recebe a resposta do backend e publica `door/{id}/access-result` no tópico MQTT com **QoS 1** para garantir entrega.

**Se GRANTED:**
```json
{
  "decision": "GRANTED",
  "userId": "7b3cf58e-353f-48de-b2fd-6f203d64d3f8",
  "userName": "Ana Souza"
}
```

Além disso, o broker enfileira automaticamente um comando `UNLOCK`:
```
POST /iot/devices/ctrl-bloco-a-lab-101/commands
{ "command": "UNLOCK", "ttlSeconds": 60 }
```

E publica `door/{id}/command` com o payload do UNLOCK.

**Se DENIED:**
```json
{
  "decision": "DENIED",
  "reason": "PERMISSION_DENIED"
}
```

---

### Etapa 5 — Ação na fechadura (Firmware)

O firmware aguarda `door/{id}/access-result` em um loop com timeout de 3 segundos:

```cpp
unsigned long waitStart = millis();
while (millis() - waitStart < 3000) {
  mqttClient.loop();
  if (accessResultReceived) break;
}

if (!accessResultReceived) {
  // Timeout → aplicar política offline (HW-008)
  applyOfflinePolicy();
  return;
}

if (accessDecision == "GRANTED") {
  digitalWrite(RELAY_PIN, HIGH); // Destrava fechadura
  setLED(GREEN);
  buzzerShortBeep();
  delay(3000);                   // Mantém aberta por 3 segundos
  digitalWrite(RELAY_PIN, LOW);  // Trava novamente
  setLED(OFF);
} else {
  setLED(RED);
  buzzerLongBeep();
  delay(2000);
  setLED(OFF);
}
```

## Estados de erro e seus tratamentos

| Situação | Motivo no log | Ação no firmware |
|---|---|---|
| Controlador não cadastrado | `CONTROLLER_NOT_FOUND` | DENIED — LED vermelho |
| Credencial não cadastrada | `CREDENTIAL_NOT_FOUND` | DENIED — LED vermelho |
| Usuário sem permissão | `PERMISSION_DENIED` | DENIED — LED vermelho |
| Timeout da resposta MQTT | — | Política offline (HW-008) |
| Broker offline | — | Política offline (HW-008) |
| Backend retorna erro 5xx | — | DENIED por segurança |

---

## Política offline (HW-008 — pendente)

Quando o broker ou o backend estão indisponíveis, o firmware aplica o matching **local** usando os templates biométricos sincronizados na memória do ZN-53X:

```
1. Firmware não consegue publicar (sem conexão MQTT)
   OU aguarda access-result e recebe timeout (3s)
        │
        ▼
2. Verifica os N últimos templates carregados nos slots do ZN-53X
3. Se matching local encontrado → concessão local (UNLOCK temporário)
4. Registra o evento em LittleFS (filesystem local no ESP8266)
5. Ao reconectar, envia os logs offline para POST /iot/access-log/batch
```

> ⚠️ **Status:** HW-008 ainda não implementado. O firmware atual nega acesso em caso de timeout como política conservadora (fail-secure).

---

## Gap atual — PERM-005

A função `processAccessAttempt` atualmente verifica apenas **PERM-001** (permissão direta usuário → sala). Os demais níveis (PERM-002, PERM-003, PERM-004) são consultados pela função `verifyAccess`, mas a integração ainda não foi feita.

Isso significa que, no fluxo IoT atual:
- Um usuário com permissão via **perfil** (`PERM-003`) **não consegue** abrir a porta pela biometria
- Um usuário com permissão via **tipo de sala** (`PERM-002`) **não consegue** abrir a porta pela biometria
- Apenas permissões **diretas** (`PERM-001`) funcionam no fluxo físico

A correção está priorizada no backlog como **PERM-005**.

## Latência esperada

| Segmento | Tempo estimado |
|---|---|
| Leitura biométrica (ZN-53X matching) | 200–800ms |
| Publicação MQTT (device → broker) | < 50ms (LAN) |
| Chamada HTTP broker → backend | < 20ms (rede interna) |
| Consulta ao banco (4 níveis) | < 10ms |
| Publicação MQTT (broker → device) | < 50ms |
| **Total estimado** | **300ms – 1s** |

O timeout de 3 segundos no firmware oferece margem confortável mesmo em condições de rede degradada.
