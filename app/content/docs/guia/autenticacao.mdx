O sistema utiliza **better-auth** para gerenciar autenticação. Toda a segurança é baseada em sessões por **cookie `HttpOnly`** — sem JWT no localStorage, o que elimina o risco de roubo de token via XSS.

## Visão geral

```
Usuário → POST /auth/sign-in
              │
              └── better-auth valida credenciais
                      │
                      ├── Inválidas → 401 Unauthorized
                      └── Válidas   → cria session no banco
                                          │
                                          └── Set-Cookie: auth_session=...
                                                  (HttpOnly · Secure · SameSite=Lax)
```

A partir desse ponto, todo request do browser enviará o cookie automaticamente. O backend valida a sessão em cada rota protegida.

---

## Fluxo de login

### Via portal web

1. Acesse `http://localhost:3000` (ou o domínio de produção)
2. Clique em **Entrar** no canto superior direito
3. Informe e-mail e senha do administrador
4. O sistema redireciona para a página inicial autenticado

### Via API direta

```http
POST /auth/sign-in/email
Content-Type: application/json

{
  "email": "admin@ifsp.edu.br",
  "password": "Admin@123"
}
```

**Resposta de sucesso (`200 OK`):**

```json
{
  "user": {
    "id": "01951234-abcd-7000-8000-000000000001",
    "name": "Administrador",
    "email": "admin@ifsp.edu.br"
  },
  "session": {
    "id": "...",
    "expiresAt": "2025-08-01T00:00:00.000Z"
  }
}
```

O cookie `auth_session` é definido automaticamente na resposta.

---

## Fluxo de logout

```http
POST /auth/sign-out
```

O backend invalida a sessão no banco e limpa o cookie. Nenhum corpo de request é necessário — o cookie é enviado automaticamente pelo browser.

## Sessão atual (`/me`)

Para obter os dados do usuário autenticado:

```http
GET /auth/get-session
```

**Resposta (`200 OK`):**

```json
{
  "user": {
    "id": "01951234-abcd-7000-8000-000000000001",
    "name": "Administrador",
    "email": "admin@ifsp.edu.br",
    "emailVerified": true,
    "createdAt": "2025-01-01T00:00:00.000Z",
    "updatedAt": "2025-07-01T00:00:00.000Z"
  },
  "session": {
    "id": "...",
    "userId": "01951234-abcd-7000-8000-000000000001",
    "expiresAt": "2025-08-01T00:00:00.000Z"
  }
}
```

Retorna `null` se não houver sessão ativa.

## Redefinição de senha

O fluxo de forgot/reset password é gerenciado pelo better-auth com tokens de uso único enviados por e-mail.

### Passo 1 — Solicitar redefinição

```http
POST /auth/forget-password
Content-Type: application/json

{
  "email": "admin@ifsp.edu.br",
  "redirectTo": "http://localhost:3000/reset-password"
}
```

O backend gera um token com TTL curto e envia um e-mail com o link de redefinição. No frontend, a página correspondente é `/forgot-password`.

### Passo 2 — Redefinir a senha

Ao clicar no link do e-mail, o usuário é redirecionado para `/reset-password?token=...`. A página extrai o token da URL e envia:

```http
POST /auth/reset-password
Content-Type: application/json

{
  "token": "token-recebido-por-email",
  "newPassword": "NovaSenha@456"
}
```

**Resposta de sucesso (`200 OK`):**

```json
{ "status": true }
```

Após a redefinição, o token é invalidado e o usuário pode fazer login com a nova senha.

## Guard de autenticação no backend

Todas as rotas de escrita utilizam o helper `requireAdmin`, que valida a sessão e confirma que o usuário é administrador:

```ts
// Exemplo de uso em uma rota Fastify
const session = await requireAdmin(request, reply);
if (!session) return; // reply já foi enviado com 401
```

Se a sessão for inválida ou o usuário não for administrador, o helper responde automaticamente com `401 Unauthorized` e o handler encerra sem executar a lógica de negócio.

---

## Guard no frontend

O frontend aplica guards de autenticação no `beforeLoad` das rotas protegidas via TanStack Router:

```ts
// Exemplo de rota protegida
export const Route = createFileRoute("/users")({
  beforeLoad: async ({ context }) => {
    const session = await context.queryClient.ensureQueryData(
      sessionQueryOptions()
    );
    if (!session?.user) {
      throw redirect({ to: "/" });
    }
  },
});
```

> ⚠️ O guard no frontend é apenas **UX** — ele redireciona o usuário para evitar flicker de interface. A segurança real é garantida pelo guard server-side em cada endpoint da API.

---

## Segurança

| Aspecto | Implementação |
|---|---|
| Armazenamento da sessão | Cookie `HttpOnly` — inacessível via JavaScript |
| Hash de senha | Argon2 (padrão do better-auth) |
| Token de reset | UUID de uso único com TTL curto |
| Proteção CSRF | `SameSite=Lax` no cookie |
| Validação de admin | Verificada server-side em toda rota protegida |
| Credenciais biométricas | Armazenadas com constraint `UNIQUE` — duplicatas rejeitadas no banco |

## Configuração do better-auth

O better-auth é configurado em `server/src/lib/auth.ts`:

```ts
import { betterAuth } from "better-auth";
import { drizzleAdapter } from "better-auth/adapters/drizzle";
import { db } from "@/db";

export const auth = betterAuth({
  database: drizzleAdapter(db, { provider: "pg" }),
  emailAndPassword: {
    enabled: true,
    requireEmailVerification: false,
  },
  session: {
    expiresIn: 60 * 60 * 24 * 7, // 7 dias
    updateAge: 60 * 60 * 24,      // renova a cada 24h de uso
  },
});
```

As tabelas `user`, `session`, `account` e `verification` são gerenciadas automaticamente pelo better-auth via Drizzle ORM.
